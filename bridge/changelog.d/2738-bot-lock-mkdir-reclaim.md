- **Last-resort bridge token lock no longer relies on `mkdir(1)` being exclusive (#2738).** On Ubuntu 26.04, uutils `mkdir` 0.10.0 let several concurrent creators of one path all succeed (11 of 200 rounds of 20 creators on a GitHub runner; GNU `mkdir` and bash noclobber 0 of 200). The token lock's no-flock/no-python tier used `mkdir` for its claim and its sole-reclaimer token, so two contenders could both start — the `start-lib.test.sh` `[mkdir]` race flake that evicted #2736/#2745 from the merge queue (xtrace showed both contenders creating the reclaim token and the claim). The tier now creates both with bash noclobber (`O_CREAT|O_EXCL`, a builtin); paths and the `flock unavailable; using mkdir fallback` line are unchanged, and a directory claim left by an older `start.sh` is reclaimed like any stale claim. A waiting contender also refuses when the claim it lost to was replaced during its wait (inode + ctime via `find -printf`), so it never deletes a fresh claimant's claim before that claimant records its pid. New tests (a `mkdir` that always succeeds, a legacy directory claim, a deterministic replaced-claim case) fail against the old code; `race_diag` prints winners, the pid file and each contender's output when a race miscounts. `start-lib.test.sh` passed 20 of 20 runs on ubuntu-26.04 (the old code failed in roughly 4 of 10).
