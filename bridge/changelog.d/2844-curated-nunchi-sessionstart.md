- **Curated memory sessions inject the node-global nunchi snapshot for the owner's own bridge only (#2844).** `setting_sources=[]` Claude sessions (unrestricted owner-operator, audience-scoped, every non-owner profile) never read `settings.local.json`, where `install-nunchi.sh` registers `nunchi/sessionstart.sh`, and the curated `--settings` layer that replaces it carried only `load-memory.sh` and `distill/pending-drain.sh` — so on an unrestricted owner bridge (gongyung, 2026-11-21: 0 of 9 bridge sessions in 7 days had a `## nunchi working memory` block, while governed yukson/daegyo had 12/12) the facts nunchi collected were never read back. `build_curated_memory_settings()` now appends `nunchi/sessionstart.sh` to `SessionStart` when `owner_nunchi_injection_allowed()` holds: `curated` mode, no route audience, `CCC_NODE_ISOLATION_PROFILE=fleet`, and the new `utils/memory_policy.owner_global_memory_gate()` — resolved `owner-operator` (exactly one allowlisted owner) and a session scope other than `shared-all` (alias spellings and the legacy unsafe override included). The node-global write sink (`__main__._build_global_local_sink_worker`) now uses that same gate, unchanged in behavior, so read and write sides cannot drift. Non-owner profiles, `shared-all`, audience routes and external isolation get no nunchi hook; `off` mode still builds no curated layer. Takes effect on a node only after the bridge is redeployed; the observed transcript block on gongyung is recorded on the issue separately.
