- **`bridge-watchdog.sh` no longer mistakes a Matrix frontend for the Telegram bridge (#2176).** The Matrix frontend runs the same `python -m telegram_bot --path $HOME` command line, so the pgrep fallback counted it as "Telegram is up" and a dead Telegram bridge was never restarted while Matrix stayed healthy (a Termux node's crond, 2026-10-08). Both the `bot.pid` alive check and the fallback now apply `bridge/start.sh`'s channel rule: a process whose `/proc/<pid>/environ` carries `CCC_CHANNEL=matrix` is a different service; an unreadable environ or any other value still counts as Telegram, so a live bridge is never turned into a false "down". The restart now calls `start.sh` with `CCC_CHANNEL` / `SESSION_STORE_PATH` / `CCC_BOT_ENV_FILE` / `CCC_MATRIX_CONFIG_PATH` unset, so a crond started from a Matrix shell cannot steer it to the Matrix channel (or into the #2177 refusal). The log line `start.sh exit=` now records the real exit code — `$(ts)` in the same `echo` reset `$?`, so it always logged 0. Debounce and the start lock are unchanged. `bridge-watchdog.test.sh` adds six cases (Matrix-only alive → restart, Telegram alive next to Matrix → no restart, `bot.pid` recycled onto the Matrix pid → restart, unreadable environ → no restart, Matrix caller env → neutral start, failed start → real exit code logged); four fail against the previous script. Stand-in processes are single `python3` processes reaped on exit.
