- **Termux restart-cmd ships as `scripts/termux-restart-frontends.sh`, and its Matrix step now proves the restarted frontend survives instead of comparing generation names (#2175, DOC-3768 ④).** The node-local `restart-frontends.sh` restarted the Telegram bridge through `bridge-current`, then made the runit Matrix frontend follow the pointer and logged `matrix restarted: running=<gen> want=<gen>` as soon as the new cmdline carried the wanted generation — on 2026-10-09 that line reported success twice while Matrix was crash-looping on `ModuleNotFoundError: aiohttp`, and self-update recorded the tick as activated. The step now waits for the bridge's own `health.json` to show a process started at/after the restart on the wanted generation (`runtime_generation.python_prefix`), then holds `CCC_MATRIX_SURVIVE_SECONDS` (60) requiring the same pid throughout, `sv status` uptime ≥ window for that pid (runit resets it on every crash) and `service.state == available`; otherwise it exits 3 so self-update classifies the restart as failed and notifies. The pointer is never rolled back by the script (Telegram serves the same generation; the previous target stays in `bridge-current.prev-<ts>`). The window is truncated to what `CCC_BRIDGE_RESTART_DEADLINE_EPOCH` leaves (floor 20 s); a busy Matrix still defers to a detached follower. New read-only modes: `--verify [seconds]` judges the current process with the same rule, `--dry-run` shows pointer/running/sv state. Install: `printf 'exec bash %s/ccc-node/scripts/termux-restart-frontends.sh\n' "$HOME" > ~/.claude/self-update.restart-cmd`. `termux-restart-frontends.test.sh` 22/22 (hermetic fakes for `sv`, `bridge-current.sh`, health.json).
