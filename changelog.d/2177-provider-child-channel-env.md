- **Provider children no longer inherit their frontend's channel selection (#2177, proposal 1).** The Matrix frontend's agent tool shell carried `CCC_CHANNEL=matrix` and `CCC_MATRIX_CONFIG_PATH`, so a Telegram lifecycle command or `Config.load` run there resolved the Matrix frontend. Every provider child spawn path now withholds the frontend-selection keys (`CCC_CHANNEL`, `CCC_MATRIX_CONFIG_PATH`, `CCC_MATRIX_INITIALIZE`, `SESSION_STORE_PATH`, `CCC_BOT_ENV_FILE`; new `bridge/utils/channel_environment.py`): Piri and crush drop them; Claude (Agent SDK) and Codex, whose transports merge `os.environ` under an overlay and cannot delete a key, receive empty values, which `start.sh` (`${CCC_CHANNEL:-telegram}`) and `Config.load` treat as unset. `BOT_DATA_DIR` and `LOGS_DIR` deliberately stay: the memory hooks (`distill-journal.sh`, nunchi feeds, `jev-review.py`) and `ccc_doctor` locate this frontend's journals and session store through `BOT_DATA_DIR`, and `start.sh` re-derives both from `--path`. The bridge process's own environment is untouched (the Matrix frontend still reads `CCC_MATRIX_*` flags at runtime). A Telegram `start.sh --stop` typed in a Matrix agent shell now targets Telegram without `--channel` and leaves the Matrix frontend running. Known limit: `Config.load` inside such a child resolves `channel=telegram` with the frontend's `BOT_DATA_DIR`; `start.sh` re-derives the data directory, and a direct `python -m telegram_bot` from an agent shell is not a supported lifecycle path (before this change it started a second Matrix frontend). `danso_runtime` now treats a blank `CCC_BOT_ENV_FILE` as unset when guarding the workspace. `tests/test_channel_environment.py` adds 12 cases (6 fail against the previous code: Config.load, Claude, crush, and the composed Piri / Codex / audience-scoped Codex pool child environments); `tests/test_start_channel_guard.py` adds the end-to-end provider-child `--stop` case.
