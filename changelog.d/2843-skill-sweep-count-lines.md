- **Skill sweep logs whole promotion-stage/autoinstall counts; the usage report says why a skill is `unknown` (#2843, part).** The sweep's `promotion-stage` and `autoinstall` lines log the summary JSON cut at 500 bytes, so on 12/12 nodes they ended inside `blocked[]` and could not be parsed. Those lines stay as they are. Each is now followed by a fixed-format count line built from the same JSON: `promotion-stage-counts mode= status= staged= blocked= blocked_codes=<code>:N,... errors= error_codes= repaired=` and `autoinstall-counts installed= blocked= blocked_reasons=<first word>:N,... newly_blocked= would_install= deferred= failed= pending= prescreen_archived= dry_run=`. The hook path in `skill-review.sh` logs the same autoinstall line. Codes are checked against `^[a-z0-9_-]{1,64}$` and anything else is counted as `other`. Skill names, draft ids and paths are never logged. The promotion count line is also written when a run fails: a run with staging errors exits 2, and the failed line kept only an absent `.code`. In `ccc-skill-usage-report.py node`, each `unknown` skill now carries `unknown_reason` (`unsafe-permissions` / `metadata-invalid` / `other`) and its ContractError `reason_code`. The report adds `unknown_reasons` (per-family counts) and `unknown_reason_codes`. A directory without SKILL.md (e.g. the runtime `skills/synced/` bucket) is counted as `not-a-skill` and no longer listed as an unknown skill. `aggregate` adds `totals.unknown_reasons` and `unknown_reasons_nodes`; a report from before this change is not guessed at. The `unknown/unreadable` classification in `ownership.py` is unchanged and still fails closed.
