- **`start.sh` no longer acts on the Matrix channel when a Telegram lifecycle command runs from a Matrix provider shell (#2177).** A provider shell spawned by the Matrix frontend inherits `CCC_CHANNEL=matrix` plus that frontend's `SESSION_STORE_PATH` / `CCC_MATRIX_*`; running the Telegram restart there stopped the live Matrix frontend and launched a second Matrix frontend that crash-looped on the `MatrixStore` lock (a Termux node, 2026-10-08). `start.sh` manages only the Telegram bridge — its pid, supervisor and token-lock files live in `<path>/.telegram_bot` whatever the channel, and the Matrix frontend is never started through it (systemd/runit exec python directly) — so `--restart`, `--stop` and a start (`--daemon` / foreground) that resolve to `matrix`, inherited or via `--channel matrix`, now exit `10` before anything is stopped, naming the target channel and the fix. New `--channel telegram` overrides the inherited channel and drops the Matrix-scoped `SESSION_STORE_PATH` / `CCC_BOT_ENV_FILE` / `CCC_MATRIX_*`; `--restart` forwards it to the start it spawns. `--status` is unchanged; the in-tree restart refusal (exit 5) now prints `target-channel=`. The `restart`, `prepared-start` and `stop-drain` shell suites start from a neutral channel so they pass from a Matrix shell. Scrubbing channel variables from provider children (proposal 1 in the issue) is not part of this change: child hooks resolve `BOT_DATA_DIR` for the distill journal and nunchi feeds, so removing it would misroute Matrix memory. `tests/test_start_channel_guard.py` adds 9 cases; 7 fail against the previous script, including "Telegram `--stop` from a Matrix shell kills the Matrix frontend" and "`--channel matrix --stop` kills the Telegram bridge".
