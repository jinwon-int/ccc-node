- **`start.sh` no longer acts on the Matrix channel when a Telegram lifecycle command runs from a Matrix provider shell (#2177).** A provider shell spawned by the Matrix frontend inherits `CCC_CHANNEL=matrix` plus that frontend's `SESSION_STORE_PATH` / `CCC_MATRIX_*`; running the Telegram restart there stopped the live Matrix frontend and launched a second Matrix frontend that crash-looped on the `MatrixStore` lock (gongyung, 2026-10-08). The Matrix frontend is never started through `start.sh` (systemd/runit exec python directly), so `--restart`, `--stop` and a start (`--daemon` / foreground) that resolve to `matrix` without an explicit channel now exit `7` before anything is stopped, naming the target channel and the fix. New `--channel telegram|matrix` overrides the inherited channel and drops the other channel's `SESSION_STORE_PATH` / `CCC_BOT_ENV_FILE` / `CCC_MATRIX_*`; `--restart` forwards it to the start it spawns. `--status` is unchanged. The in-tree restart refusal (exit 5) now prints `target-channel=` and the `--channel telegram` hint. Scrubbing channel variables from provider children (proposal 1 in the issue) is not part of this change: child hooks resolve `BOT_DATA_DIR` for the distill journal and nunchi feeds, so removing it would misroute Matrix memory. `tests/test_start_channel_guard.py` adds 8 cases; 6 fail against the previous script, including "Telegram `--stop` from a Matrix shell kills the Matrix frontend".
